# v0.3.2 Grant And Acquisition Surface Audit

Last updated: 2026-04-08  
Task: `V03-R2-006-T01`

## Scope

This audit covers the current lane-owned grant and acquisition surfaces for
`V03-R2-006-T01`:

- `src/sim/domains/people/**`
- `src/sim/domains/people/relationshipEngine.ts`
- `tests/**`
- `docs/releases/**`

The goal is to answer three questions before the grant baseline chain
continues:

1. Which acquisition sources are already live today?
2. Which grant dependencies are present but not yet consumed by the current
   runtime path?
3. Which seams can the social lane lock now without crossing the integrator
   boundary in `src/sim/phases/**`?

## Repo truth at the start of the grant chain

### Marriage acquisition already has a strong people-domain seam

Marriage was already the most lane-ready acquisition path:

- `src/sim/domains/people/marriage.ts` owns deterministic candidate selection,
  offer generation, scout effects, and acceptance semantics.
- `src/sim/domains/people/marriageOfferRegistry.ts` already reconstructs
  bounded offer state, reject cooldowns, and same-household concurrency seams.
- Current phase wiring in `src/sim/phases/phase_prospects.ts` only wraps the
  best available marriage offer into the live `prospects_window`.

That means marriage already had:

- deterministic generation
- bounded replay-safe metadata
- a lane-owned domain seam that could be reused by a broader acquisition view

### Inheritance claims already have a claimant registry seam

Inheritance claims were also lane-ready:

- `src/sim/domains/people/successionRegistry.ts` owns the canonical succession
  line and claimant registry.
- `buildInheritanceClaimProspect(...)` already projects a bounded claimant
  packet into the prospect model.
- `src/sim/domains/people/successionSummaries.ts` and the existing preview and
  bounded-snapshot surfaces already expose claimant and line summaries without
  re-running succession logic in the UI.

The live phase wrapper still decides when to surface that claim inside the
runtime `prospects_window`, but the claim semantics themselves were already
domain-owned.

### Grant acquisition was still phase-owned and arrears-only

Grant generation was the weak point at audit start:

- The only live grant prospect generation still lived in
  `src/sim/phases/phase_prospects.ts`.
- That path generated a `grant` prospect only when arrears were present.
- The current grant formula used a simple pressure rule:
  `arrears.coin + floor(arrears.bushels / 100)`.
- The current grant path did not consult:
  - seeded liege favor
  - portfolio manor count or capacity
  - known-house relevance
  - any manor source registry

In other words, marriage and inheritance already had lane-owned semantics with
the phase wrapper acting as a shell, while grant acquisition was still encoded
as shell behavior with no people-domain registry underneath it.

## Dependencies already available for a better grant seam

### Seeded liege relationship data already existed

`src/sim/domains/people/relationshipEngine.ts` already locked non-uniform
turn-zero liege relationships:

- player head to liege target: `A 68 / R 60 / T 14`
- liege to player head target: `A 58 / R 58 / T 16`

That meant the fiscal packet requirement for relationship-driven grants was
already satisfiable in-lane. The missing piece was a read helper and an
explicit grant eligibility rule that actually consumed that score.

### Portfolio capacity data already existed in bounded form

The economy lane had already locked:

- portfolio placeholder state on `state.portfolio.positions`
- deterministic portfolio analysis and DOE reporting
- manor-count reporting in `src/sim/domains/economy/fiscalDoe.ts`

That meant the grant lane could safely treat:

- current manor count
- bounded capacity headroom
- explicit overhead bands

as stable inputs without reopening the economy schema.

### World topology already exposed deterministic manor candidates

The world lane had already locked bounded topology views and bundled world
data. That provided a safe read-only source for:

- anchor manor id
- deterministic travel distance
- nearby manor ordering
- crown-domain versus mesne holding distinctions

The remaining gap was that there was still no live actor-to-title bridge
between:

- `state.locals.liege.id` and
- the crown-domain actor ids inside the world files

That mismatch matters because it prevents the social lane from claiming that a
runtime grant source is fully title-accurate today. A proxy seam can still be
safe and useful, but the audit needs to call that limitation out explicitly.

## Fiscal packet gaps at audit start

Against `docs/releases/v0.3_FISCAL_SPINE_PACKET.md`, the missing grant pieces
were concrete:

### 1. No grant origin inventory

The fiscal packet expects liege grants to function as one of the expansion
sources. At audit start there was no canonical surface for:

- liege demesne candidates
- dispossessed manor candidates
- deterministic bounded source ranking

### 2. No explicit grant eligibility contract

The packet says grants should depend on:

- seeded liege relationship score
- fiscal standing
- portfolio capacity and admin overhead

At audit start none of those were expressed as a reusable domain contract.

### 3. No bounded acquisition window outside the live phase wrapper

Marriage and inheritance already had domain semantics, but there was still no
single lane-owned acquisition window that could project:

- marriage
- grant
- inheritance claim

through one deterministic bounded ordering rule for preview or snapshot
consumers.

## Safe lane-owned interpretation for `v0.3.2`

The strict integrator boundary means this tranche cannot rewire
`src/sim/phases/phase_prospects.ts`. The safe interpretation for the grants
chain is therefore:

- define a canonical people-domain grant registry
- define explicit grant eligibility and dossier summaries
- define deterministic grant source proxies backed by the locked world and
  economy seams
- expose a canonical acquisition window on preview and bounded snapshot
  surfaces
- leave the live accept and reject runtime path in the phase wrapper untouched

That keeps the lane inside allowed paths while still giving later integrator
work a domain seam to adopt instead of more shell logic.

## Audit outcome

At the end of `T01`, the repo truth supported the following plan:

- marriage: reuse the existing people-domain seam
- inheritance: reuse the existing claimant registry seam
- grant: create the missing people-domain registry, eligibility, and source
  seams
- preview and snapshot: expose a canonical acquisition window from the
  domain-owned builders

The main explicit boundary remains:

- live phase-owned grant prospect generation is still arrears-only until
  integrator wiring adopts the new registry seam

That limitation is acceptable for the `v0.3.2` lane tranche because the social
lane can now lock the canonical contract without editing the orchestrator.
