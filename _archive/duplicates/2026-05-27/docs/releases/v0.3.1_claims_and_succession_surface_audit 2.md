# v0.3.1 Claims And Succession Surface Audit

Task: `V03-R1-004-T01`  
Date: `2026-04-05`  
Lane: `codex/v0.3-lane-social-mechanics`

## Scope

This audit inventories the current heir, claimant, and succession-order
surfaces in the repo, then compares them to the locked `v0.3.1` goal of a
deterministic succession-line map plus bounded `inheritance_claim`
prospects.

## Current succession state in repo truth

### 1. The only canonical player-house succession field is `house.heir_id`

Current runtime state carries a single direct heir pointer on the player
house:

- `src/sim/types.ts` exposes `house.heir_id` on `HouseState`,
  `HouseSummary`, and bounded snapshots.
- `src/sim/state.ts` initializes the field to `null` at world start.
- `src/sim/turn.ts` and `src/sim/phases/phase_succession.ts` recompute and
  persist that single pointer during turn resolution.

There is no current line object, claimant registry, claimant score table,
or house-level succession structure beyond this one resolved heir id.

### 2. Heir selection already has deterministic ordering rules

`src/sim/phases/phase_succession.ts` implements the current heir law:

- children are partitioned into sons first, then daughters
- within each sex branch, ordering is age-descending and then id-ascending
- descendant search recurses through each child branch before moving to the
  next branch
- if no eligible child branch exists, the fallback searches the male line
  through fathers and collateral male descendants

Two distinct selectors already exist:

- `computeHeirId(state)` resolves the general heir pointer
- `computeAdultSuccessorId(state)` applies a minimum succession age of 15

That means the repo already has a deterministic ordering rule, but only as
an internal resolver that returns one winner rather than a surfaced ordered
line.

### 3. Succession resolution is still player-house-only and imperative

When the player head dies, `resolveSuccessionPhase()` in
`src/sim/phases/phase_succession.ts`:

- chooses an adult successor from the current resolver
- falls back to a synthetic cadet heir if no valid successor exists
- swaps `state.house.head` to the heir
- resolves the heir's spouse from `spouse_of` kinship edges
- rebases head-centered relationship edges onto the new ruler
- recomputes the next `house.heir_id`
- emits `succession` and `heir_selected` house-log events

This is a runtime transition, not a reusable succession registry. The
current implementation resolves one successor at a time and does not retain
an ordered next-in-line map for later claimant or UI use.

## Current claimant surfaces

### 4. `inheritance_claim` exists only as a thin prospect hook

`src/sim/phases/phase_prospects.ts` currently defines the entire claimant
surface:

- an `inheritance_claim` prospect type exists in `src/sim/types.ts`
- the prospect is generated only when `computeHeirId()` returns `null`
- the prospect signature is only `inheritance_claim:${state.house.head.id}`
- the generated prospect carries only the current head as
  `subject_person_id`
- predicted effects only set the flag `inheritance_claim_active`

There is no current claimant registry, no claimant identity list, no
target-line metadata, no claimant rationale, and no tie back to a bounded
succession order. The existing prospect is therefore a placeholder surface,
not a full claims model.

### 5. No explicit claimant data exists elsewhere in the repo

The audit found no current people-domain structure for:

- claimant ids
- claim strength or relevance
- target house or target line metadata
- cadet branch ranking
- line snapshots or overflow summaries

The only claim-adjacent runtime artifact today is the thin
`inheritance_claim` prospect path above.

## Current view and evidence surfaces

### 6. Current UI-ready succession visibility is limited to heir signals

The current surfaced outputs are narrow:

- `src/sim/domains/people/playerHousehold.ts` exposes an `heir` badge in the
  household roster
- `src/sim/court.ts` exposes the same `heir` badge in court roster rows
- `src/sim/householdView.ts` rebases relationship labels after succession so
  former children become siblings or parents relative to the new head
- `src/sim/domains/ai/evidence.ts` and `src/sim/turn.ts` already serialize
  `succession` and `heir_selected` evidence/log events
- `src/sim/domains/people/knownHouseSummaries.ts` exposes coarse external
  house heir signals such as `has_male_heir`, `heiress_possible`, and
  `heir_indicator`

What is missing is an ordered player-house succession line or claimant
summary surface. Current outputs tell the player who the present heir is,
not who comes next after that or why.

## Existing marriage-to-succession interactions

### 7. Marriage currently affects succession through kinship persistence, not through explicit claimant logic

The current repo already preserves several marriage-linked invariants that
matter for succession:

- `tests/v025_dev_b_realism.test.ts` and
  `tests/v0272_hotfix_p0_regressions.test.ts` lock that daughters may marry
  out of court residence while remaining in `state.house.children`, so their
  lineage stays available for succession accounting
- `tests/sim/peopleFirst_parentage_stability.test.ts` locks that succession
  does not rewrite existing `parent_of` lineage edges
- `src/sim/phases/phase_succession.ts` resolves the new ruler's spouse from
  surviving `spouse_of` kinship edges, with deterministic lexicographic
  tie-breaking when multiple spouse matches exist
- `src/sim/phases/phase_prospects.ts` suppresses `inheritance_claim`
  generation whenever a valid heir already exists, so marriage and fertility
  outcomes indirectly affect claim visibility by changing whether the house
  has an heir

These are real marriage-to-succession effects, but they are indirect.
Marriage edges do not yet contribute explicit claimant relevance, cadet
branch promotion, or ordered-line scoring.

## Gaps against the locked `v0.3.1` target

### Gap 1. No succession-line map exists yet

The scope lock calls for a claims and inheritance baseline with a
succession-line map. The repo currently resolves only one heir and one
adult successor at a time. There is no reusable ordered line structure for
player or non-player houses.

### Gap 2. No bounded claimant registry exists yet

The current `inheritance_claim` prospect is not backed by claimant data. It
has no claimant roster, no branch metadata, and no bounded explanation of
why a claim exists or how strong it is.

### Gap 3. Marriage edges are preserved, but not yet scored into succession relevance

Current marriage-linked behavior preserves spouse and lineage edges, but the
succession resolver does not yet use marriage links to adjust ordered-line
priority, claimant relevance, or cadet branch visibility.

### Gap 4. Current visibility is heir-only rather than line-aware

The player can currently see:

- who the heir is
- when succession happened
- coarse heir signals for known houses

The player cannot currently see:

- the next several successors in order
- overflow or bounded-line summaries
- who counts as a claimant when no heir exists
- why a claimant is relevant

## Existing evidence in tests

- `tests/sim/heir_law_v029.test.ts` confirms the male-line collateral
  fallback when no living children exist.
- `tests/v0272_hotfix_p0_regressions.test.ts` confirms stable spouse
  selection during succession and preserved lineage after daughters marry
  out.
- `tests/sim/peopleFirst_parentage_stability.test.ts` confirms lineage does
  not get rewritten after head-of-house changes.
- `tests/v0232_dev_b_patch.test.ts` confirms current heir visibility is a
  badge on deduped household roster rows rather than a separate row type.

## Audit conclusion

The repo already contains a deterministic heir resolver and a working
succession transition for the player house. What it does not yet contain is
the `v0.3.1` claims baseline:

- no ordered next-in-line map
- no claimant registry
- no claimant metadata carried by `inheritance_claim` prospects
- no marriage-edge claimant relevance layer
- no line-aware output surface for the UI or snapshots

That leaves `V03-R1-004-T01` complete as the baseline audit and identifies
the follow-on work for schema definition, bounded claim generation,
marriage-aware line ordering, and output surfaces.
