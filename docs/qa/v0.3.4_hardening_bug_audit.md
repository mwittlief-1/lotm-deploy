# v0.3.4 Hardening Bug Audit

## Scope

This audit enumerates the v0.3 hardening backlog around widowhood, remarriage, multiple-heir handling, and orphaned family-graph edges. The goal is to identify the smallest safe fix slices before behavior-changing work begins in `V03-R4-001-T02` and `V03-R4-001-T03`.

Guardrails for the follow-on fixes:

- preserve deterministic replay unless the task explicitly allows a golden shift
- prefer carving domain-owned repair helpers over broad phase rewrites
- keep `src/sim/turn.ts` out of scope
- treat roster, court, and snapshot surfaces as consumers of canonical family state, not parallel sources of truth

  - verifies a widowed head can die on the same turn without corrupting household roster rendering

## Detailed Findings

### 1. Widowhood is canonical in the death phase, but consumers still reconstruct it

`src/sim/phases/phase_demography.ts` is the authoritative writer for same-turn widowhood:

- it sets `state.house.spouse_status = "widow"`
- it records the `widowed` house log event
- it decides which person is the survivor and which is the deceased

But downstream consumers still reconstruct widowhood independently:

- `src/sim/court.ts` prefers the last `widowed` log event, then falls back to alive/dead mismatch
- `src/sim/domains/people/playerHousehold.ts` only uses alive/dead mismatch

Risk:

- same-turn badge rendering can drift between the household roster and court roster if only one surface is updated
- widowhood fixes can look correct in replay logs but still be wrong in bounded read models

Recommended `T02` slice:

- add a single domain-owned widowhood resolver that returns the canonical widowed person for the current state/log context
- make `court.ts` and `playerHousehold.ts` consume that helper instead of re-deriving widowhood independently

### 2. Remarriage is governed by inconsistent “living spouse” rules

The player-facing marriage path already distinguishes stale married state from a living spouse:

- `src/sim/marriageMarket.ts` allows a widow if a spouse edge exists but the spouse is dead

But the world marriage generator still blocks on any spouse edge:

- `src/sim/demography.ts` says “Skip anyone with a spouse edge already (no remarriage in v0.2.8).”

The player household eligibility gate is also narrower than the market’s candidate filter:

- `src/sim/domains/people/marriage.ts` only offers the head when there is no spouse object and `spouse_status !== "widow"`

Risk:

- widowed characters can be eligible in one path and silently excluded in another
- repairs to spouse edges can accidentally create or suppress remarriage offers across different systems

Recommended `T02` slice:

- define one shared “has living spouse” helper in the people domain
- switch both world marriage generation and player marriage eligibility to that helper
- keep spouse-edge exclusivity repair in the same change so dead edges do not continue to shadow remarriage

### 3. Heir selection still mixes canonical registry state with legacy household fallbacks

`src/sim/phases/phase_succession.ts` resolves succession from:

- `deps.computeAdultSuccessorId(state)`
- `fallbackHeirIdFromHouseMembers(state)`
- legacy household arrays if the chosen heir is not already loaded

It then derives the spouse by calling `spouseIdFromKinship(state, heir.id)` and mutates household head/spouse pointers directly.

The regression in `tests/v0272_hotfix_p0_regressions.test.ts` shows why this is brittle:

- multiple spouse edges can exist for the heir
- the sim currently survives because it uses a stable tie-break, not because graph integrity is guaranteed

Risk:

- duplicate heir surfaces across roster, court, and claimant summaries
- succession choosing a mechanically stable but semantically wrong spouse
- emergency-heir creation masking an earlier graph-integrity bug

Recommended `T03` slice:

- make one people-domain helper return the canonical successor plus canonical spouse context
- use that helper in `phase_succession.ts` before any head/spouse mutation
- add graph-integrity tests that fail on duplicate spouse or duplicate heir paths instead of tolerating them

### 4. Inheritance-claim suppression depends on clean heir nullability

Both prospect systems gate inheritance claims on heir absence:

- `src/sim/phases/phase_prospects.ts`
- `src/sim/domains/people/grantAcquisitionRegistry.ts`

That is the correct design, but it means stale heir state has broad downstream effects:

- a false non-null heir suppresses valid claims
- a false null heir emits inheritance claims when the household graph still has a live successor path

Risk:

- orphaned or duplicate edges turn into market/prospect bugs instead of staying localized to succession

Recommended `T03` slice:

- run graph repair before inheritance-claim prospect generation
- explicitly test “no heir because graph is broken” versus “no heir because the line is genuinely empty”

## Expected Risk Areas For The Follow-On Fixes

### `V03-R4-001-T02`

Highest-risk surfaces:

- same-turn `widowed` house log emission
- `spouse_status` transitions
- marriage candidate filtering for widows
- replay-visible roster/court badge output

Expected safe approach:

- reuse the same deterministic ordering and same-turn log semantics
- avoid broad rewrites in `phase_demography`
- only normalize widowhood and living-spouse resolution, then add regression coverage around both player and world marriage paths

### `V03-R4-001-T03`

Highest-risk surfaces:

- head/spouse reassignment during succession
- inheritance-claim suppression
- roster/court/heir summary consistency
- emergency-heir fallback

Expected safe approach:

- repair targeted graph cases deterministically before consumers render them
- make the phase consume canonical people-domain outputs instead of layering new heuristics into report readers

## Recommended Task Sequencing

1. `V03-R4-001-T02`
   - widowhood normalization
   - living-spouse normalization
   - remarriage eligibility consistency
2. `V03-R4-001-T03`
   - multiple-heir path repair
   - orphaned spouse/parent edge repair
   - inheritance-claim suppression consistency
3. `V03-R4-001-T04`
   - simplify whichever hotspots remain after the accepted bug fixes

## Exit Criteria For This Audit

- widowhood, remarriage, heir, and orphan-edge bugs are enumerated with reproduction evidence
- each hotspot is mapped to its current read/write seam
- the first two hardening slices have a constrained plan and explicit risk notes
