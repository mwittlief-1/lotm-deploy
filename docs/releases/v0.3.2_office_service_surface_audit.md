# v0.3.2 Office And Service Surface Audit

Epic: `V03-R2-004`  
Audit Task: `V03-R2-004-T01`  
Date: `2026-04-05`  
Lane: `codex/v0.3-lane-social-mechanics`

## Scope

This audit inventories the current office-adjacent surfaces that already
exist in the simulation, identifies which seats are effectively required
versus optional today, and maps the holder transition points that later
office and service tasks must wrap without breaking deterministic replay.

The audit is limited to the social lane write surfaces plus read-only
inspection of the current legacy court implementation so later tasks can
carve a safe seam instead of guessing at behavior.

## Current house-court seat surfaces

The live seat model still sits in the legacy court layer, not in the new
court domain:

- `src/sim/court.ts` owns the current `houses[player_house_id].court_officers`
  mapping.
- The active role keys are still `steward`, `clerk`, and `marshal`.
- The default behavior is `steward` only.
- `clerk` and `marshal` remain opt-in legacy carry-forwards unless the
  `A/B/C` court tuning variant explicitly enables them.

The current structure is deterministic but narrow:

- `ensureCourtOfficers()` seeds or repairs officer IDs using the isolated
  `"court"` RNG stream.
- dead holders are replaced by removing the mapping and reseeding the role
  deterministically
- officer persons are still generated as generic male stubs
- no explicit vacancy window, appointment reason, or tenure record is kept

## Current service-record surfaces

Service persistence exists, but only as a broad generic scaffold:

- `src/sim/types.ts` defines a top-level `service_records[]` array with the
  minimal fields `id`, `person_id`, `serving_actor_id`, `role`,
  `start_turn_index`, and `end_turn_index`
- `src/sim/peopleFirst.ts` only guarantees that `service_records` exists as
  an array during migration/upsert
- `src/sim/court.ts` mirrors the current officer map into
  `sr_<house>_<role>` records through `syncCourtOfficerServiceRecords()`

That mirror keeps the current legacy court functioning, but it is not yet a
full office registry:

- replacements overwrite the existing record's `person_id` and reset
  `start_turn_index`
- the structure does not preserve explicit appointment or dismissal causes
- there is no house versus realm office distinction
- non-family retainers do not yet carry a dedicated cost or compensation
  basis

## Required versus optional seats today

The current live seat requirements are narrower than the v0.3 backlog asks
for:

- `steward` behaves like the only required player-house seat in default
  play, because the legacy court code reseeds it whenever the role is
  absent
- `clerk` is optional
- `marshal` is optional

Those rules are enforced implicitly through the legacy court seeding logic,
not through an explicit seat registry.

## Current holder transition points

There are three real transition points in the current code:

1. New-run and preview-load migration:
   `COURT_OFFICERS_MIGRATION_STEP` calls `ensureCourtOfficers()`, so
   officer scaffolding is regenerated whenever that migration path runs.
2. Legacy court repair:
   `ensureCourtOfficers()` removes dead holders, keeps surviving legacy IDs,
   and reseeds missing officer persons deterministically.
3. Report projection:
   `buildCourtRoster_v0_2_4()` and `turn.ts` project the current officer map
   into `court_roster_v1`, but only as a derived report surface.

Important non-transitions:

- `successionRegistry.ts` currently models heirs and claimant ordering, but
  it does not yet hand off into service placement or office succession
- bounded snapshots intentionally omit `service_records`, so no downstream
  reader can rely on office tenure state yet
- marriage and known-house mechanics touch court membership views, but not
  office holder assignment

## Realm-side adjacent surfaces

There is no realm office registry yet in the social lane domains. The
nearest adjacent facts are:

- `src/sim/domains/world/types.ts` holding records carry
  `holder_actor_id`, `immediate_lord_actor_id`, `service_basis`, and
  `vacancy_rule_family`
- institution records and parish scaffolds carry patron or priest pointers
- these world and institution surfaces describe control and tenure context,
  not staffed offices with service history

That means `V03-R2-004-T04` will need a new realm-office seam rather than a
small patch on an existing registry.

## Audit conclusions

The safe seam for the next task is clear:

- keep the live officer behavior in place for now
- extract a new court-domain office registry that mirrors the current
  `steward`/`clerk`/`marshal` seat model
- give required seats an explicit one-turn vacancy cap
- define a typed service-record contract that later tasks can persist
  without mutating the legacy `service_records[]` shape directly

That supports the backlog sequence:

- `T02` can define deterministic house and realm office schemas
- `T03` can later bridge required house seats and retainer costs into live
  behavior
- `T04` can add realm holder registries and tenure transitions without
  reusing the old `court_officers` map as the source of truth
