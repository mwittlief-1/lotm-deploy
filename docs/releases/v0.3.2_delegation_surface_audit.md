# v0.3.2 Delegation Surface Audit

Last updated: 2026-04-05
Task: `V03-R2-003-T01`

## Scope

This audit covers the current lane-owned delegation surfaces for `V03-R2-003-T01`:

- `src/sim/domains/court/**`
- `src/sim/domains/people/**`
- `tests/**`
- `docs/releases/**`

Read-only dependency notes below reference existing economy seams because two of the current court-budget actions are executed through the canonical fiscal settlement helpers.

The goal is to answer three questions before the delegation registry work begins:

1. Which current actions actually consume court decision budget today?
2. Which of those actions are good candidates for deterministic delegation in `v0.3.2`?
3. Which adjacent surfaces should explicitly stay out of scope for the `v0.3` delegation tranche?

## Candidate delegation surfaces

### 1. Delegated gift and offering execution

The best existing seam for delegated external court actions is the fiscal settlement scaffold path:

- contract selection lives in `src/sim/domains/economy/schema.ts`
- scaffold construction and receipt-coupled payment live in `src/sim/domains/economy/storeReceiptWriters.ts`
- budget charging is already normalized before the payment mutation lands

That makes `liege_gift` and `church_offering` good delegation candidates as long as the new registry only changes explicit efficiency metadata such as:

- budget cost adjustment
- payment amount adjustment
- deterministic cap or floor rules

The important boundary is that delegation should sit above scaffold creation and budget charging, not inside the ledger writer itself. The ledger writer is already the canonical dangerous-write seam.

### 2. Delegated scouting

`marriage_scout` is the clean people-domain candidate for delegation because the action already:

- has its own explicit budget key
- has a distinct fixed cost
- produces a deterministic quality modifier rather than an immediate kinship or succession mutation

For `v0.3.2`, delegated scouting should stay limited to efficiency-only cost shaping. It should not:

- alter candidate pool ordering
- change RNG keys or offer draw count
- bypass the existing scout energy or coin payment path

### 3. Delegated maintenance

Maintenance is a valid future delegation target by scope lock, but it does not yet exist as an active runtime mechanic in the lane-owned code. The current codebase has:

- receipt taxonomy mentions for `expense.maintenance` and `expense.household_admin` in `docs/releases/v0.3_FISCAL_SPINE_PACKET.md`
- no active maintenance domain seam under `src/sim/domains/court/**`, `src/sim/domains/people/**`, or the current economy runtime code

That means `T03` cannot "wire delegation into existing maintenance logic" because there is no such logic yet. The only safe `v0.3.2` interpretation is to introduce a new bounded maintenance seam with explicit deterministic inputs and tests, not to infer maintenance from unrelated expenses.

## Surfaces that should stay out of delegation v0

### Inbound marriage handling stays player-facing

`marriage_inbound` is a current budget consumer, but it is a poor delegation target in `v0.3.2` because it directly changes:

- marriage state
- kinship edges
- household membership and residence
- dowry coin outcomes
- unrest or relationship effects

The backlog already distinguishes scouting from inbound handling, and that split is correct. Delegation v0 should reduce or reshape the cost of gathering options, not automate the dynastic commitment itself.

### Ordinary obligation settlement is adjacent, not delegated

`settleEconomyObligationCounterparty(...)` in `src/sim/domains/economy/obligationRegistry.ts` is deterministic and once-per-turn per counterparty, but it is not currently a court-budget action. Delegation v0 should not reclassify ordinary `church_due` or `liege_due` settlement into court-budget spend.

### Extraordinary levy service remains a schema hook only

The accepted payment contract table still exposes `service_placeholder` only for `extraordinary_levy`. That remains a future service/offices concern, not part of the `v0.3.2` delegation baseline.

## Deterministic-only contract for `v0.3.2`

The locked `v0.3.2` delegation scope should be interpreted narrowly:

- delegation is an efficiency registry, not an autonomous court AI
- no random success rolls, soft chances, or hidden quality variance
- no new phase ordering or integrator wiring
- no recomputation of relationship, marriage, or ledger semantics in snapshot consumers
- no actor assignment or office-holder staffing simulation yet

In practice, the safe effect palette for the next tasks is:

- explicit budget cost reduction
- explicit payment or upkeep scaling
- explicit summary metadata for court and portfolio snapshots

Anything broader should wait for office/service records in `V03-R2-004` or later agenda work.

## Handoff into `T02` through `T05`

### `T02` registry contract

The delegation registry should express deterministic effect metadata only. The most stable starter shape is a court-owned registry keyed by action family, with enough metadata to answer:

- whether delegation is active for the action family
- what explicit budget-cost or payment-efficiency modifier applies
- which summary label should surface in bounded outputs later

### `T03` delegated settlement and maintenance hooks

`T03` should split cleanly:

- wire gift and offering delegation above fiscal settlement scaffold creation
- introduce a fresh bounded maintenance seam rather than pretending one already exists

### `T04` delegated scouting

`T04` should wire delegation only into the scouting path in `src/sim/domains/people/marriage.ts`, not into inbound acceptance or rejection.

### `T05` snapshot outputs

The eventual snapshot surface should summarize delegation state so downstream consumers can read:

- which delegation families are active
- which explicit efficiency modifiers are in play
- what budget impact changed this turn

Consumers should not have to infer delegation status by re-running budget or marriage logic.

## Audit outcome

The current repo truth supports a narrow, deterministic delegation v0:

- delegate `gift_liege`
- delegate `offering_church`
- delegate `marriage_scout`
- introduce maintenance as a new bounded seam before it can be delegated
- keep `marriage_inbound` player-facing

That keeps the `v0.3.2` delegation work inside explicit cost and summary mechanics, without smuggling in office staffing, autonomous agenda logic, or non-deterministic court behavior.
