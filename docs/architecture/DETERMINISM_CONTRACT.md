# Lords of the Manor — Determinism Contract

**Status:** Final Canon Batch A v0.1  
**Authority:** QA/runtime spine / CPO-CTO canon draft for CEO approval  
**Source basis:** Runtime reset canon, PLUMB/evidence-gate consolidation, P0/P1/P2 packets  
**Scope:** Defines deterministic expectations, baseline discipline, and review evidence standards.

---

## 1. Purpose

Determinism is required so that long-run simulation, runtime proofs, Codex changes, and QA gates remain trustworthy.

The determinism contract protects:

- seeded world generation;
- repeatable proof outputs;
- stable regression tests;
- non-perturbation properties;
- baseline drift discipline;
- receipt/provenance traceability;
- human review confidence.

---

## 2. Deterministic Domains

The following should be deterministic under fixed seed and fixed inputs:

- reference-world loading;
- generated run state;
- derived read models;
- proof reports;
- overlay IDs where generated by proof/runtime path;
- receipt IDs where generated by proof/runtime path;
- fixture scenarios;
- non-random resolution rules;
- seeded random draws;
- QA summaries and fingerprints.

If nondeterminism is unavoidable, it must be isolated, documented, and excluded from deterministic gates.

---

## 3. Seed and Scenario Rule

A seed/scenario should produce stable outputs for the same code and data.

World context, home manor identity, local context, derived modifiers, demographic projections, and proof artifacts must not drift without causal explanation.

---

## 4. Fingerprint Rule

Reference World and Generated Run State fingerprints must remain stable when a change is not intended to affect them.

If a change does affect a fingerprint, the review packet must explain:

- which layer changed;
- why it changed;
- whether the change was intended;
- which source file/code path caused it;
- whether a baseline update is requested;
- why the update is narrow and safe.

---

## 5. Non-Perturbation Rule

Non-perturbation tests should prove that a feature or presentation path does not alter unrelated state.

Example principle:

> Prospect presentation/rejection should not perturb unrelated world state.

But non-perturbation does not freeze obsolete behavior. If old behavior is wrong, it may be changed with row-level proof and approval.

---

## 6. Baseline Drift Discipline

Baseline drift is not automatically bad, but unexplained drift is unacceptable.

A baseline update may be accepted only when:

- there is row-level owner proof;
- receipts/log evidence exists;
- causal explanation is supplied;
- affected rows are identified;
- update scope is narrow;
- no unrelated drift is bundled;
- no red-zone behavior is introduced;
- the appropriate authority approves.

Blanket baseline updates are prohibited.

---

## 7. Evidence Requirements for Codex Work

A Codex review packet should include:

- task/lane ID;
- authorized scope;
- changed files;
- tests run;
- pass/fail results;
- fixture outputs or artifact paths;
- source-truth layer touched;
- receipts/provenance generated;
- baseline/fingerprint effects;
- stop-rule checks;
- RFIs and blocked decisions;
- recommendation for next step.

Routine green-zone work may produce lighter packets. Yellow/red-zone work requires fuller evidence.

---

## 8. Test Failure Handling

Codex may repair mechanical test failures inside an authorized lane when:

- failure cause is local and mechanical;
- repair does not cross stop rules;
- product behavior is not changed beyond the authorized scope;
- baseline updates are not smuggled in;
- repeated failures are capped by autonomy budget.

Codex must escalate when:

- tests fail because of ambiguous product behavior;
- repair would alter canon or product defaults;
- baseline drift lacks explanation;
- red-zone behavior is implicated;
- repeated repair loops show no progress.

---

## 9. Product vs Proof Determinism

A proof can be deterministic while still being product-invalid.

Passing tests do not authorize:

- live economy writes;
- live lifecycle runtime;
- A/R/T mutation;
- marriage market behavior;
- claims enforcement;
- UI integration;
- turn integration;
- reference/generated mutation.

A deterministic unauthorized behavior is still unauthorized.

---

## 10. Required Stop on Ambiguous Drift

If Codex cannot explain a changed output in source-truth terms, it must stop or log an RFI.

It may not “accept snapshots” merely because tests can be updated.

---

## 11. Determinism Contract for Future Specs

Future mechanical specs should include their own deterministic acceptance criteria, especially for:

- population/demography projections;
- A/R/T movement previews;
- economy/ledger/obligation fixtures;
- food sufficiency;
- incident probability;
- CourtOS capacity;
- turn-pressure simulations;
- knowledge confidence.

Until those specs exist, Codex should avoid deriving final numeric tests from doctrine alone.
