# LoM UX Audit — v0.3.2 Portfolio Holdings, Ledger Scope, and Selector Baseline

**Task:** `V03-R2-005-T01`  
**Scope:** inventory the current gameplay surfaces that expose manor holdings, resolved ledger evidence, and the new read-only portfolio stub; document where scope is already stable versus where it is still implicit; and leave a task-ready handoff for the follow-on selector and scoped-ledger work.  
**Constraint:** audit only. No new selector behavior or post-`v0.3` holdings controls in this task.

- `manor`: the resolved chronicle and actionable next-turn controls
- `portfolio`: additive context and bounded outlier exceptions

What it does not yet have is a shared selector or a shared scoped-ledger model.

## 2. Current portfolio baseline in the UI

The accepted `V03-R2-001` work already gave the UI a safe read-only baseline:

- bounded snapshot includes `portfolio`
- `PlayScreen` renders `PortfolioOverviewPanel`
- `playScreenPortfolio.ts` converts snapshot totals and outlier rows into a presentation surface

What the current portfolio stub does well:

- totals are additive and clearly portfolio-scoped
- outliers are bounded to exception rows instead of trying to render a full multi-manor ledger
- the panel is explicitly read-only and does not imply new controls

What it does not do yet:

- no portfolio-versus-manor toggle
- no selected-manor concept
- no receipts or diff-ledger scope switch
- no selector path from an outlier row into a deeper manor-scoped explanation

This is the correct shipped baseline for `T01`: portfolio exists as context, not yet as a navigable interaction model.

## 4. The core UX mismatch to solve next

The shell is now carrying both:

- a local-manor chronicle
- a portfolio-wide summary

That is good, but the boundary is still implicit.

The player can currently read:

- “these are my manor’s resolved food / coin / unrest changes”
- “these are my portfolio totals and top exceptions”

The player cannot yet do the next logical step:

- move from portfolio context to a selected manor
- keep receipts and ledger explanation aligned with that selected scope
- tell whether a detail card is speaking for the whole portfolio or just the current manor without inferring it from prose

So the next UI risk is not missing numbers. The risk is scope bleed:

- portfolio totals could start looking actionable when they are not
- manor receipts could look portfolio-wide when they are not
- outlier rows could look like navigation affordances without stable selection behavior behind them

## 5. Scope rules that should stay stable

These rules should guide `T02` through `T04`.

### Rule 1: Chronology stays manor-scoped by default

The resolved chronicle should remain local unless the UI explicitly says otherwise:

- sticky chips
- diff ledger
- turn report
- decisions
- receipts modal

These surfaces should not silently become portfolio-wide just because a portfolio panel now exists above them.

### Rule 2: Portfolio summary stays additive and non-actionable

Until the selector lands:

- portfolio totals are context, not direct controls
- outliers are exception summaries, not full ledger replacements
- portfolio rows should not imply that actions are being applied across all manors

### Rule 3: Selected manor must become explicit before scoped ledger changes land

When a selector is added, the UI needs an explicit selected-scope contract such as:

- `portfolio` summary scope
- `selected manor` detail scope

The shell should never require the player to guess whether a card is still talking about the anchor manor or about the currently selected outlier manor.

### Rule 4: Receipts stay evidence, not the selector itself

The receipts explainer should respond to a selected scope later, but it should not become the place where scope is chosen.

Scope selection belongs in the holdings / portfolio shell first. Receipts should inherit that state.

### Rule 5: Outliers stay bounded

The outlier list should remain:

- bounded to a short exception list
- deterministic in order
- framed as “what deserves attention next,” not as a replacement for a full manor table

That keeps the IA aligned with the earlier gameplay-shell rule: the main card owns headlines, not exhaustive registries.

## 6. Selector and scope requirements for follow-on tasks

### `V03-R2-005-T02` needs one presentation-safe contract

The next contract task should define a UI-owned view model that answers:

- what is the current portfolio summary?
- which manor is the current anchor manor?
- which manor is selected, if any?
- what label should the shell show for the active scope?
- which outlier rows can promote a manor into selected scope?
- which ledger/receipt surfaces are still portfolio summary versus selected-manor detail?

Important boundary:

- `T02` should consume accepted snapshot surfaces
- it should not recompute portfolio math in `src/ui`
- it should not infer selection from label text alone

### `V03-R2-005-T03` should add one visible scope toggle, not many

The first visible interaction should be minimal:

- portfolio summary remains the top-level card
- one clear manor-scope toggle or selected-manor affordance appears in the holdings surface
- current-manor and selected-manor language is explicit

The task should avoid:

- parallel selectors in multiple cards
- a second portfolio card elsewhere in the page
- turning the portfolio panel into a miniature spreadsheet

### `V03-R2-005-T04` should let ledger evidence inherit scope

Once a selected manor exists, the scoped evidence path should follow:

- receipts viewer respects the selected scope
- diff ledger headline can reflect whether it is still current-manor or selected-manor detail
- selector state stays UI-only and never mutates sim state

This means the ledger and receipts path should follow the selector, not reinvent it.

## 8. Task-ready conclusions

1. The current UI already has a valid two-scope baseline: manor chronicle below, read-only portfolio summary above.
2. The main missing contract is not more holdings math. It is one explicit selected-manor scope model that the shell, ledger, and receipts can all share.
3. Portfolio totals should remain additive summary context, while outlier rows should become the narrow bridge into a selected-manor detail state.
4. Diff ledger and receipts should stay manor-scoped until `T04` gives them inherited scope from the selector; they should not silently shift to portfolio-wide language first.
5. `T02` should therefore define selector and scope semantics, `T03` should render the first visible holdings toggle, and `T04` should let the ledger/receipts path inherit that state.

This audit should be treated as the canonical UX inventory for the `V03-R2-005` portfolio selector pass.
