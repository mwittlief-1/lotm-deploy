# LoM UX Audit — v0.3.0 Gameplay Field Homes

**Task:** `V03-R0-004-T01`  
**Scope:** Audit the current gameplay screen, identify where each field lives today, map duplicate facts to one canonical display home, and document modal/debug surfaces to preserve in the v0.3 UX pass.  
**Constraint:** Audit only. No mechanic or data-contract changes.

---

   - left: `ManorStatePanel`
   - right: `TurnReportPanel`

   - right: `KnownHousesPanel`
   - right: `IntelPanel`
   - right: `RelationshipDrawerPanel`

The main legibility issue is not missing data. It is repeated data shown with inconsistent tense and equal visual weight.

## 3. Dedupe map

The rule for the next UI tasks should be simple: each fact gets one canonical home, and any secondary appearance must be either:

- a compact summary pointer
- a debug-only surface
- a future modal/detail surface

### Canonical homes

| Fact family | Canonical home | Secondary surface allowed | Current duplication to collapse |
| --- | --- | --- | --- |
| Net turn changes | `DiffLedgerPanel` | future receipts viewer / "Explain Changes" modal | Turn Report "At a glance" repeats the same delta story. |
| Current manor stocks | `ManorStatePanel` | future sticky resource chips | Turn Report "At a glance" repeats current totals. |
| Food accounting detail | `TurnReportPanel` > `Food & stores` | future food chip modal | Manor State stores, Decision helper copy, and food deltas all compete for the same concept. |
| Obligations state | `TurnReportPanel` > `Obligations` | `DecisionsPanel` as action entry only | The same totals appear in both cards without a clear "results vs choices" split. |
| Household status | `HouseholdPanel` | future household detail modal | Court size appears in both collapsed and expanded household content. |
| Prospects | `ProspectsPanel` | prospect detail modal | Legacy marriage window is a fallback only and should stay secondary. |
| Known houses | `KnownHousesPanel` | house detail modal | None needed elsewhere on the main screen. |
| Intel | `IntelPanel` | intel detail modal | None needed elsewhere on the main screen. |
| Events | `EventsPanel` | event detail modal | Diff Ledger should summarize impacts, not restate event cards. |
| Relationship edges | debug accordion / debug screen | none | Relationship Drawer should not compete with Known Houses as a first-class card. |
| Raw registries and exports | debug screen | none | Keep out of the main gameplay hierarchy. |

### Duplicate clusters that matter now

1. Resource state is currently split across `DiffLedgerPanel`, `ManorStatePanel`, `TurnReportPanel`, and `DecisionsPanel`.
   - Food, coin, and unrest each appear as both delta and total in more than one card.
   - This is the main cause of "same fact, different card" fatigue.

2. Obligations use the same numbers in both `TurnReportPanel` and `DecisionsPanel`.
   - This is a valid dual-home case only if the copy clearly distinguishes:
   - `last 3 years` / already happened
   - `now choose` / next-turn payment intent

3. Household and court size are repeated inside the same card family.
   - The collapsed household summary already provides the headline.
   - Expanded household detail should add roster and log depth, not restate the same court-size headline.

4. "Why" appears in two different forms.
   - `DiffLedgerPanel` already gives deterministic one-line attribution.
   - `Top drivers` is useful raw context, but it should not compete with the ledger as a second summary system.

## 4. Recommended canonical hierarchy for the next UI tasks

This is the recommended single-column order for the v0.3 gameplay shell:

1. Identity strip and sticky resource chips
   - turn
   - ruler/house/heir/energy when available
   - coin / food / unrest as always-visible chips
2. Council Agenda
3. Explain Changes entry
   - opens grouped/raw receipts viewer
   - Diff Ledger remains the visible summary
4. Manor snapshot
5. Household
6. Food and obligations detail
7. Prospects
8. Known Houses
9. Intel
10. Events
11. Decisions
12. Debug accordion

Interpretation:
- top of screen = "what changed" and "what matters now"
- middle = explain/detail cards
- bottom = decisions and debug

## 5. Modal candidates

These surfaces are good candidates for the reusable modal sheet planned in later tasks:

- `Explain Changes`
  - grouped receipts view
  - raw receipts view
  - chip-to-detail routing for coin, food, and unrest
- Prospect detail
  - summary, costs, effects, confidence, expiry
- Known house detail
  - head, heir stability, A/R/T, house-level notes
- Intel detail
  - current vs remembered entries in one focused view
- Event detail
  - title, why, effects, supporting notes
- Household detail
  - roster, locals, house log

The modal should own dense explanation. The main card should own the headline.

---

## 6. Debug surfaces to preserve

These should remain accessible, but they should move behind a toggle, accordion, or dedicated debug route instead of staying in the main reading flow:

- `Debug/Log` entry to `RunLogScreen`
- `AllPeopleRegistryPanel`
- `RelationshipDrawerPanel`
- `ProspectsPanel` log details
- `TurnReportPanel` consumption breakdown details
- `ManorStatePanel` unrest breakdown details

Preserve them exactly because they are useful for audits and replay debugging. De-emphasize them because they are not primary gameplay facts.

---

## 7. Task-ready conclusions

1. The current play screen already contains enough data for the v0.3 gameplay shell. The next UX pass should primarily re-home and re-weight information, not add new fact families.
2. `DiffLedgerPanel` is the natural visible summary, and the future receipts viewer should become the canonical explain surface behind it.
3. `TurnReportPanel` should keep current-turn accounting, but it should stop competing with `DiffLedgerPanel` and `ManorStatePanel` for headline resource state.
4. `DecisionsPanel` should keep action controls, but repeated obligation and labor facts need stronger timing copy so "before decisions" and "next turn" stop blending together.
5. `RelationshipDrawerPanel`, `RunLogScreen`, and `AllPeopleRegistryPanel` are valuable and should be preserved as debug surfaces, not removed.
