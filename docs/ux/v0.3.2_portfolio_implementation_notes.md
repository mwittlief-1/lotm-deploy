# LoM UX Implementation Notes — v0.3.2 Portfolio Scope and Selector

**Epic:** `V03-R2-005`  
**Closeout task:** `V03-R2-005-T06`  
**Scope:** summarize what the UI lane shipped for the v0.3.2 portfolio scope pass, record the stable selector and evidence contract, and leave a clean handoff for content, playtest, and later map-enabled work.

## 1. Shipped in v0.3.2

### T01 — portfolio scope audit
- `docs/ux/v0.3.2_portfolio_scope_audit.md` remains the canonical inventory for manor holdings, portfolio totals, outlier rows, and the ledger-scope gap that existed before selector work landed.
- The audit conclusion held: the missing piece was not more holdings math. It was one shared selected-manor scope model that the shell, diff ledger, and receipts path could all read.

### T02 — portfolio scope contract
- The UI lane introduced a presentation-only portfolio contract around three stable concerns:
  - additive portfolio summary
  - deterministic tracked-manor selector options
  - selected-manor detail and evidence-scope rules
- The contract reads accepted bounded snapshot surfaces and avoids recomputing portfolio rollup math inside rendering code.

### T03 — visible holdings toggle
- `PortfolioOverviewPanel` now shows one explicit scope toggle for `Portfolio summary` versus `Current manor detail`.
- Portfolio totals remain the top-level card, while the selected-manor follow-up stays compact and readable instead of turning into a second spreadsheet or ledger.
- Outlier rows remain bounded exception rows and now read as follow-up cues rather than full accounting replacements.

### T04 — deterministic manor selector and inherited evidence scope
- The holdings panel now exposes deterministic tracked-manor selection using the contract order locked in `T02`.
- Sticky chips, the diff ledger headline, and the receipts viewer now inherit that selector state instead of inventing a second scope model.
- When the selected manor is not the current anchor manor, the UI now says that directly and keeps the resolved ledger/receipt trail anchored to the current manor chronicle rather than implying hidden multi-manor evidence exists.

## 2. Current portfolio UX contract

The gameplay shell should now be read with these rules:

1. `PortfolioOverviewPanel` owns the additive portfolio summary.
   - Portfolio totals stay at the top of the card.
   - Outlier rows remain bounded exceptions.
   - Selector state lives here first.

2. `selected manor detail` is explicit and UI-owned.
   - Manor selection is deterministic.
   - Selection does not mutate sim state.
   - The holdings shell can follow a different manor without pretending that all other cards automatically became multi-manor.

3. `DiffLedgerPanel` is now scope-aware, not scope-rewritten.
   - If the selected manor matches the current manor, the ledger reads as the live selected-manor chronicle.
   - If the selected manor does not match the current manor, the panel says that it is still pinned to the current manor chronicle.

4. `ReceiptsViewerPanel` follows the same selector state.
   - The modal now carries explicit scope labeling before the grouped/raw receipt modes.
   - It does not pretend non-anchor manors have a separate resolved receipt trail when the bounded snapshot does not expose one.

5. Sticky chips remain current-manor headline facts.
   - They now carry scope-aware helper text when selected-manor detail is active elsewhere in the shell.

This is the canonical v0.3.2 UI contract unless a later backlog task explicitly reopens portfolio scope design.

---

## 3. Stable rules for follow-on work

- Keep portfolio totals additive and non-actionable unless a later task explicitly adds batch planning controls.
- Keep selector ordering deterministic and UI-only.
- Keep outlier rows bounded and legible; they should remain cues, not full manor ledgers.
- Keep evidence surfaces honest about what the bounded snapshot does and does not expose.
- Extend the existing selector/evidence seam rather than creating new scope state inside chips, receipts, or ledger subviews.

## 4. Deferred after v0.3.2

The following remain intentionally outside the shipped portfolio scope pass:

- `V03-R2-005-T05` map-centering remains blocked behind `V03-XMAP-001` and merged map/topology surfaces.
- Non-anchor manors still do not expose independent resolved ledger or receipt trails in the bounded snapshot.
- No new portfolio-wide batch action planner was introduced.
- `ManorStatePanel`, `TurnReportPanel`, and `DecisionsPanel` still describe the current manor chronicle and next-turn controls rather than a multi-manor planning shell.

These should stay deferred unless a later backlog task explicitly reopens them.

## 5. Handoff for content and playtest work

Content and playtest follow-on work should treat the current portfolio shell as stable enough to reference directly:

- content can now write explicit portfolio-versus-selected-manor helper copy against one shared selector contract
- playtests can verify whether players understand when they are reading additive context versus one manor’s bounded follow-up
- future map-enabled work should attach to the existing selector rather than replacing it

Suggested review questions for the next playtest pass:

> Can a player tell when the shell is speaking about the whole portfolio versus one selected manor without inferring that from prose alone?

> When a non-anchor manor is selected, does the player understand why the ledger and receipts still reference the current manor chronicle instead of assuming the UI is broken?
