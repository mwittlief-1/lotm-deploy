# LoM UX Audit — v0.3.4 Playtest Ops And Export Surfaces

**Task:** `V03-R4-003-T01`  
**Scope:** inventory the current export, reporting, and playtest-facing evidence surfaces in the gameplay shell; document where those surfaces live today; and call out the gaps that block a clean receipt-bundle workflow.

---

## 1. Current export access

The gameplay shell currently exposes exports in three places:

| Surface | Current path | What the player can do now | Source refs |
| --- | --- | --- | --- |
| Decisions footer | Gameplay shell -> Decisions footer | Export Run Summary JSON, Export Full Run JSON | `src/ui/panels/DecisionsPanel.tsx`, `src/App.tsx` |
| Debug accordion | Gameplay shell -> Debug accordion -> Run log & exports | Open Run Log, Export Run Summary JSON, Export Full Run JSON | `src/ui/panels/PlayScreen.tsx`, `src/ui/playScreenChrome.ts` |
| Run Log screen | Run Log screen header | Export Run Summary JSON, Export Full Run JSON | `src/ui/panels/RunLogScreen.tsx`, `src/App.tsx` |

The export actions themselves are stable, but the access pattern is fragmented:

1. The same two JSON downloads appear in multiple places without one canonical playtest handoff.
2. The best route into deeper reporting is hidden behind a debug accordion label instead of a playtest-facing action.
3. There is still no export action that packages receipts, summaries, and raw run evidence together.

---

## 2. Current reporting and evidence surfaces

Playtest reporting already depends on four existing evidence homes:

| Surface | Current path | What it explains well | Receipt-bundle readiness |
| --- | --- | --- | --- |
| Run Log screen | Run Log screen body + All People registry | Raw turn summaries, event deltas, registry inspection | Partial |
| Turn Report | Gameplay shell -> Turn Report | Resolved outcomes and player-facing summary cards | Missing |
| Council Agenda + Diff Ledger | Gameplay shell -> Council Agenda / Explain Changes | Why the shell thinks a follow-up matters | Missing |
| Receipts viewer modal | Gameplay shell -> Explain Changes / sticky resource chips | Grouped receipts, raw phases, counterparty evidence | Partial |

The receipts viewer is the strongest existing evidence surface for a future playtest packet, but it still stays modal-only and has no export convention attached to it.

---

## 3. Pain points for playtest ops

### Export fragmentation

- JSON exports are duplicated across the Decisions footer, debug accordion, and Run Log screen.
- None of those entry points explains which artifact belongs in a playtest report versus a deep debugging handoff.

### Reporting fragmentation

- Turn Report and Diff Ledger explain outcomes well, but they are not exportable.
- Receipts evidence is stronger than the raw run log for player-facing explanation, but it has to be gathered manually.
- The Run Log screen is still raw-JSON-first, which is useful for debugging but noisy for assembling a review packet quickly.

### Missing packet conventions

- No receipt-bundle naming convention exists yet.
- No seed-pack instructions tell a tester which runs or evidence slices to include.
- No bug-report template or KPI placeholder convention exists yet for v0.3.4 playtest ops.

---

## 4. Gaps against receipt-bundle expectations

A clean receipt bundle would need, at minimum:

1. One canonical export name and folder convention for the packet.
2. The run summary JSON.
3. The full run JSON.
4. Receipt evidence that is already grouped for human review.
5. Seed and scenario instructions so a tester knows which run context the packet represents.

The current shell only covers items `2` and `3` directly. Item `4` exists as a modal evidence surface, but not as an export flow. Items `1` and `5` do not exist yet.
