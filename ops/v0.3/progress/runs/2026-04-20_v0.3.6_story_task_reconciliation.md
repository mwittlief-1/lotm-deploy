# v0.3.6 Story-to-Task Reconciliation

**Date:** 2026-04-20
**Branch:** `codex/v0.3-refactor-kickoff`
**Commit:** `992aa80`

## Summary

The canonical `v0.3.6` UAT pack contains **45 user stories** (`US-01` through `US-45`).
The current `v0.3.6` control plane in `ops/v0.3/backlog.yaml` contains **19 executable tasks** (`V03-R6-*`).

That means the current backlog is **not story-native**. It is a compressed implementation backlog where each task often covers multiple stories, multiple screens, and sometimes an entire theme.

This compression is probably contributing to the current execution difficulty:

- acceptance becomes ambiguous because one task may only partially satisfy several stories
- same-lane continuation looks efficient on paper but hides unresolved story-level gaps
- operator and integrator conversations drift because tasks are implementation-shaped while UAT feedback is story-shaped

## Canonical Counts

- User stories: `45`
- `v0.3.6` executable tasks: `19`
- Average compression ratio: about `2.37 stories per task`

That average understates the real problem because the compression is uneven:

- some tasks are tight and clean
- some later-tranche tasks are carrying **6-10 stories at once**

## Practical Diagnosis

The current `19`-task graph is workable as an engineering decomposition, but it is weak as a UAT tracking model.

The biggest pressure points are:

1. `V03-R6-005-T01`
   - marriage workflow, copy, navigation, send/reject outcomes, and family-status clarity are too much for one acceptance packet

2. `V03-R6-006-T01`
   - household presence, provisioning truth, officer truth, succession readability, and demography are too many distinct player-facing concerns in one task

3. `V03-R6-007-T01`
   - dossier/person-card clarity covers too many story surfaces to prove complete with one accepted packet

4. `V03-R6-003-T03`
   - upkeep-labor explanation, placeholder-market clarity, and meat-system resolution are related, but not really the same task from a UAT perspective

## Recommendation

Before pushing much further into the remaining `v0.3.6` queue, add a story-native sidecar artifact instead of pretending the `19` tasks are enough by themselves.

Minimum corrective move:

1. Keep `backlog.yaml` task ids as the executable scheduler source.
2. Add a story coverage matrix that records:
   - `US id`
   - mapped `V03-R6-*` task ids
   - current status: `unstarted`, `in_progress`, `partially_covered`, `covered`, `accepted_as_closed`
   - notes on evidence gaps
3. Split `V03-R6-005-T01` and `V03-R6-006-T01` before treating them as clean acceptance boundaries if story-level closeout is required.

## Bottom Line

The user-story pack did **not** become a 45-task backlog.
It became a **19-task compressed engineering backlog**.

That is why the current queue looks small on paper while still feeling operationally heavy in practice.
